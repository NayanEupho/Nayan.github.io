RAG for admin work, part 1: ingestion

Part 1 of 2 · RAG · Ingestion

At the Institute for Plasma Research, a lot of day-to-day life runs on policy documents: leave rules, LTC policy, GFR rules, IT usage, and a long tail of internal procedures. The documents exist, but finding the one paragraph that answers a question is slow. Keyword search is brittle because the person asking rarely uses the same words as the policy author.

That is the problem the RAG administrative assistant was built to solve: ask a question in plain English, get an answer grounded in the actual documents, and keep every byte on-premise. This post is about the half of the system people skip in architecture diagrams — ingestion. Part 2 covers retrieval and generation.

The shape of the system

The prototype used Docling to parse PDFs, an embeddinggemma:300m model served by Ollama for embeddings, ChromaDB for vector storage, LangGraph for workflow orchestration, SQLite for session state, FastAPI for the API, and a Next.js/Bun chat UI. The generation model was Qwen2.5:72b, also served locally by Ollama on an NVIDIA A100.

The ingestion path itself is short:

  • Load and parse policy PDFs.
  • Split the text into overlapping chunks.
  • Attach metadata that describes where each chunk came from.
  • Embed each chunk.
  • Store the vector and metadata in ChromaDB.

Every hard problem is hiding in those five bullets.

Step 1: parsing PDFs is not reading text

A policy PDF is a layout document, not a text file. It has headers, footers, tables, numbered clauses, annexures, and occasionally a scanned page that is just an image. The lazy version of ingestion calls a text extractor and hopes for the best. That version produces chunks where the page number is glued to the middle of a sentence and a table becomes a vertical pile of words.

We used Docling because it understands document structure well enough to preserve reading order and tables. Even then, parsing was the first source of bad retrieval. A few failure modes showed up immediately:

  • Tables that carry the answer. Leave balances, pay bands, and eligibility matrices are often tables. If the parser flattens a table into meaningless lines, no embedding model can recover the relationship between columns.
  • Repeated headers and footers. These become high-frequency noise. If every chunk contains the same footer, similarity search starts treating it as signal.
  • Scanned annexures. Image-only pages need OCR. Without it, the chunk is empty or full of garbage, and the retriever silently loses a whole section.
  • Multi-column layouts. Reading order matters. If the parser interleaves two columns, the answer reads like two sentences were shuffled together.

The lesson: ingestion quality is a ceiling on answer quality. No prompt, reranker, or larger model fixes a chunk that never contained the answer in a readable form.

Step 2: chunking is a context decision

Chunking is usually described as a size parameter. In practice it is a decision about what context the model is allowed to see. Too small, and a clause loses the section heading that gives it meaning. Too large, and the embedding becomes an average of several topics, which makes it a poor match for any one of them.

We split documents into overlapping chunks so that a rule spanning a boundary still appears intact in at least one chunk. Overlap is a cheap insurance policy, but it is not free: duplicated text increases index size and can make the retriever return the same content twice. Deduplication at retrieval time is part of the job.

Two design choices mattered more than the exact token count:

  • Keep structural context in the text. A chunk should still know which document, section, and subsection it belongs to. We carried that in metadata, and used the section path to reconnect chunks during retrieval.
  • Store neighbour relationships. Each chunk got a chunk_index. If a retrieved chunk is cut in the middle of a rule, the retriever can pull index - 1 and index + 1 to restore a sliding window of context.

Step 3: metadata is the real retrieval feature

Vector similarity alone answers “what text looks like this query?” It does not answer “which document is this from?”, “which section is it in?”, or “what comes next?”. Metadata made the index usable as a document structure instead of a bag of vectors.

Each embedding was stored with fields like document name, page number, section and subsection, chunk index, and the section path. That enabled three kinds of connection:

  • Horizontal (sequential). chunk_index lets the retriever fetch neighbouring chunks when the answer is split across a boundary.
  • Vertical (hierarchical). The section path lets the system group chunks from the same topic even when the text does not repeat the topic name. A chunk about “dependent eligibility” inherits meaning from its parent section on “LTC rules”.
  • Cross-document. The filename lets a user target a specific document with an @filename mention, which immediately ignores millions of unrelated chunks.

This is the part I would invest in first on a rebuild. Embeddings are commodity; a good metadata model is specific to the organisation and does more for answer quality than swapping embedding models.

Step 4: embeddings have to agree with each other

Ingestion and query time must use the same embedding model, with the same preprocessing, the same normalisation, and the same dimensions. This sounds obvious until the model gets upgraded on one side of the system. A new embedding model means a full re-index; there is no partial compatibility.

We used embeddinggemma:300m locally. The small model kept ingestion cheap and made it realistic to re-embed a document collection on ordinary hardware. The trade-off is that a larger embedding model may separate near-duplicate policy language better. That is a decision to measure, not assume.

Two practical details caused trouble:

  • Batch size and timeouts. Embedding a large document one chunk at a time is slow. Batching helps, but a batch that times out leaves a partially indexed document.
  • Index versioning. If the embedding model or chunking strategy changes, old vectors and new vectors must not be mixed. Each collection needs a version, and the application needs to know which one is current.

Step 5: ChromaDB is easy until documents change

ChromaDB handled persistence and approximate nearest-neighbour search without much ceremony, which is exactly what a prototype needs. The difficult part was not the database; it was keeping it consistent with the folder of PDFs.

A WatchDog service watched an upload_docs folder and triggered re-indexing when documents were added or updated. That made the system feel automatic, but automation without idempotency is a bug factory:

  • Re-running ingestion must not duplicate chunks. Chunks need stable IDs derived from document, page, and index, so an update replaces rather than appends.
  • Deleting a document must delete its vectors. Otherwise the assistant keeps answering from a policy that no longer exists.
  • Partial failures need a retry path. A crash halfway through a PDF cannot leave the collection in a state where half the document is searchable and the other half is missing.
  • Updates need a version. The safest pattern is to build a new collection and switch an alias when it is complete, rather than mutating the live index in place.

What actually broke

Most of the debugging time went into a small number of unglamorous issues:

  • Chunks without headings. A clause like “the same shall apply to dependents” is unanswerable without the section it belongs to. Injecting the section path into the chunk text fixed more queries than any prompt change.
  • Tables treated as prose. The fix was structural: keep rows together, keep the column headers, and store the table context in metadata.
  • Duplicate content. Overlap and repeated boilerplate produced near-duplicate hits. Deduplication by document and chunk index kept the context window useful.
  • Stale answers. A policy update that only touched one page was not always re-indexed. File watching needs to compare content hashes, not just timestamps.
  • Evaluation by vibes. Early on, “looks right” was the test. That does not scale. A small set of real administrative questions with known source passages is the only way to tell whether an ingestion change helped or hurt.

What I would do differently

I would build the evaluation set before the pipeline, not after. A spreadsheet of 30–50 real questions, each with the document and page that contains the answer, turns ingestion from guesswork into a measurable system. It also makes chunking decisions testable: change the chunk size, re-run the set, and compare recall at the chunk level.

I would also treat ingestion as a versioned build artifact. Documents, parser version, chunker version, embedding model, and collection name should all be recorded together. When an answer is wrong six weeks later, the first question is which index produced it.

Finally, I would keep the ingestion service separate from the chat service. Parsing and embedding are batch work; answering questions is interactive. Coupling them means a re-index can degrade the experience of someone asking a question at the same time.
