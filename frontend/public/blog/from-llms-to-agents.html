From LLMs to agents: teaching the team

Teaching · MCP · Agents

Tools are only useful if people know when to reach for them. I delivered an internal session called “From LLMs to AI Agents” for colleagues at IPR. The goal was not to turn everyone into an agent engineer. It was to give people a working mental model of what these systems can do, where they fail, and how to use them safely in daily work.

The outline

  1. What an LLM is, briefly. A next-token predictor with a context window, not a database and not an oracle.
  2. Why a standalone model is not enough. It lacks organisational knowledge and can answer confidently from nothing.
  3. RAG. Retrieve evidence first, then generate. Show a real administrative question and the source passage the answer came from.
  4. Tools and the agent loop. The model proposes an action, the runtime executes it, the result goes back into context, repeat.
  5. MCP. A standard way to describe and call tools, so the agent runtime does not need a custom integration per system.
  6. Skills. Packaged instructions that tell an agent how to do a specific job well.
  7. Safety. Permissions, approvals, audit, and the difference between a suggestion and an action.

What resonated

The demos mattered more than the definitions. Seeing a policy question answered with a link to the document was more convincing than any diagram. Seeing an agent stop and ask for approval before a destructive action made the safety model concrete.

People wanted the boundary, not the hype. The most common questions were about failure: What happens when it is wrong? Who is responsible? Can it see things I cannot? Those are the right questions, and they are easier to answer when the architecture is explicit about permissions and evidence.

“Agent” is a vague word. Some people meant a chat assistant, some meant an automation, some meant a tool-using loop. Naming the loop and the tools separately removed a lot of confusion.

What I would change

I would spend less time on model internals and more time on a single end-to-end task. A live walkthrough — question, retrieval, tool call, approval, answer — teaches more than three slides of terminology. I would also give people a small, safe sandbox to try rather than a presentation to watch.

The session also changed how I think about internal tooling. Adoption depends on trust, and trust depends on visible evidence and reversible actions. A tool that shows its sources and asks before doing something irreversible will be used more than a clever one that does not.
