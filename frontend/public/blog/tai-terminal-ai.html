TAI: a small terminal agent in Go

Go · CLI · Agents

Most of my day happens in a terminal. The friction is small but constant: I know what I want to do, I do not remember the exact flag, and I end up in a browser searching for a man page. TAI — Terminal AI — was a small attempt to remove that context switch. It is a Go program built with Bubble Tea that takes a natural-language request and gives back the command, inline, without leaving the shell.

The repository is tai-AI-Agent.

The design constraint: stay small

The temptation with an AI CLI is to make it a platform. I wanted the opposite. TAI should start fast, show a prompt, stream a short answer, and exit. No daemon, no database, no plugin system. The model runs behind an OpenAI-compatible endpoint, which means the same binary can point at an on-prem vLLM server or a local Ollama instance.

Bubble Tea made the interface feel native: a small input, streaming output, and keyboard handling that does not fight the terminal. Go made the binary easy to distribute. The whole thing is the kind of tool that should be a single executable.

What it does

  • Takes a natural-language description of a task.
  • Asks the model for the closest command and a one-line explanation.
  • Streams the response so the user is not waiting on a blank screen.
  • Lets the user copy or edit the command instead of executing it automatically.

That last point is deliberate. An assistant that runs commands for you is a different product with a different risk profile. TAI is a command-recall tool. It suggests; the human decides.

The hard parts

Shell differences. PowerShell and Bash are not the same language. A flag that is correct in one is a syntax error in the other. The prompt has to know which shell it is targeting, and the tool has to let the user be explicit when it cannot tell.

Quoting. A command that looks fine in prose can be dangerous when a path contains a space or a variable expands unexpectedly. The model is good at the shape of a command and inconsistent about quoting. Showing the command before running it is the simplest mitigation.

Safety. Destructive commands need a clear signal. Even in suggest-only mode, a model can produce rm -rf with a path the user did not mean. Highlighting risky patterns and refusing to auto-execute them is not optional.

Latency. A terminal tool has a higher latency bar than a chat window. If the answer takes five seconds, the user has already gone back to searching. Streaming helps, but the first token still has to arrive quickly. A smaller, faster model is often the right choice for this use case.

Context. The tool does not know the current directory, the shell, or the recent commands unless you tell it. Adding just enough context — shell, OS, maybe the last command — improves answers without turning the prompt into a transcript.

What I would change next

I would add a confirmation step that can optionally execute a command, but only after an explicit keypress and a risk check. I would add a small history file so repeated questions can be recalled. And I would add a per-shell prompt template instead of asking the model to infer the shell from the question.

The broader lesson is that small tools are a good place to learn agent design. There is no orchestration graph to hide behind. The interesting questions — what context does the model need, what should it never do on its own, how fast does it need to be — are all visible in a few hundred lines.
