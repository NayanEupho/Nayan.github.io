REST vs MCP: what actually costs time

MCP · Benchmarking · Agents

When an agent calls a tool, two things happen: the model decides what to call, and the runtime performs the call. Most discussions about REST versus the Model Context Protocol (MCP) blur those together. The model-side cost is tokens and reasoning. The runtime-side cost is network, serialisation, and connection setup. They are different problems.

I built REST-vs-MCP to measure the runtime side with a fair comparison: the same operations exposed both ways, network conditions simulated, and a dashboard for the results.

What each option is good at

REST is the default because everything speaks it. It has mature tooling, caching, proxies, auth, and a mental model every engineer already has. For a single service, it is usually the shortest path.

MCP adds a protocol designed for tools: discovery, schemas, and a standard way for a host to talk to a server. The value is not raw speed. It is that an agent can discover what a server offers and call it without bespoke glue for every integration.

So the honest question is not “which is faster?”. It is “which overhead are you willing to pay?”.

The benchmark

The suite performed comparable operations over both transports and recorded latency, payload size, and connection behaviour under different network conditions. The details are in the repository; the useful part is where the time goes.

  • Connection setup. A fresh connection is expensive. A persistent session amortises it. If the agent makes one call, that setup is a large fraction of the total; if it makes fifty, it disappears.
  • Schema and discovery. MCP can tell the agent what tools exist and what arguments they take. That is valuable, but the schema still has to be sent or loaded, and it consumes context on the model side.
  • Framing. JSON-RPC adds a little envelope around each call. For large payloads it is noise; for many tiny calls it adds up.
  • Streaming and concurrency. A protocol that handles long-running calls and streams well is worth more than a few milliseconds of framing when the tool is slow.

Where REST wins

REST wins when the integration is known at build time, the calls are simple, and the infrastructure already exists. It also wins on debuggability: a curl command and a browser are often enough. If an agent calls one internal endpoint, wrapping it in a protocol adds a layer without adding much.

Where MCP wins

MCP wins when the tool surface is broad and changing, when several hosts need to talk to several servers, and when discovery matters. A document system, a cluster, and a database all expose different tools. A standard protocol means the agent runtime does not need a new integration for each one.

The token cost is the trade-off people underestimate. Every tool schema is context. A server with fifty tools can spend a meaningful part of the window describing itself before the model does any work. Tool selection and schema pruning become part of the design.

What I took away

  • Measure the workload, not the protocol. A benchmark of one call is a benchmark of connection setup.
  • Separate model cost from runtime cost. The protocol does not control how many tokens the model spends deciding.
  • Keep the tool surface small. Fewer, clearer tools beat a large catalogue, in both protocols.
  • Persist connections where possible. It is the single biggest runtime win in both cases.
