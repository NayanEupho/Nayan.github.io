Running LLMs on an 8×A100 DGX-1

Inference · vLLM · CUDA

The inference side of an on-prem AI platform looks simple from the outside: start a model server, point applications at it, done. In practice most of the work is in the parts nobody demos — GPU memory, concurrency, model versions, access control, and the day the driver upgrade has to happen without taking every existing GPU job down with it.

At IPR I worked on the serving layer for in-house RAG, agentic Kubernetes, and coding agents running on an NVIDIA DGX-1 with eight A100 80 GB GPUs. This post is a record of the decisions and the failures, especially the CUDA driver upgrade from 12.2 to 13.1.

The serving stack

We ended up with a layered setup:

  • vLLM as the high-throughput inference engine, serving OpenAI-compatible endpoints.
  • LiteLLM as the proxy in front of the model servers, handling routing, per-user API keys, limits, and a single interface for applications.
  • Langfuse for observability — requests, latency, token usage, and traces across applications.
  • A small Streamlit dashboard for key management, so users could get and rotate credentials without an operator editing configuration by hand.
  • Ollama for lighter experiments and for models that did not need vLLM’s serving features.

The proxy mattered more than expected. Once applications talk to one OpenAI-compatible endpoint, the model behind it becomes an implementation detail. We could move a workload from Ollama to vLLM, or from one quantisation to another, without changing every client.

Why vLLM, and where the time goes

vLLM’s advantage is not a single magic flag. It is a set of decisions that matter under concurrency: continuous batching, PagedAttention for KV-cache memory, and attention kernels that keep the GPUs busy. On a single request, the difference is modest. Under load, it is the difference between a queue and a service.

We evaluated vLLM against Ollama on the agentic RAG workload. The vLLM path reduced worst-case time-to-first-token from 5.1 seconds to 2.7 seconds. Average latency is the number people quote; worst-case TTFT is the number users feel. A chat interface that starts answering in under three seconds feels responsive. One that occasionally takes five feels broken even if the average is fine.

That result drove the serving decision for high-concurrency applications. Ollama remained useful for experimentation, but vLLM became the default for anything with more than a couple of simultaneous users.

VRAM is the real scheduler

On an eight-GPU node, memory is the constraint that shapes everything else. A model that fits is not the same as a model that serves well. The KV cache grows with context length and concurrency, so the question is not “does the model fit?” but “how many concurrent requests fit at the context lengths we actually use?”.

Several things helped:

  • Tensor parallelism to spread a model across GPUs when a single card could not hold it comfortably.
  • Quantisation — FP8 and Mixture-of-Experts Qwen-class models — to raise throughput without falling off a quality cliff.
  • Separate models on separate GPU sets where possible, so a large generation model did not starve an embedding or reranking model.
  • Explicit context limits per deployment. Letting every request ask for the maximum context is a good way to exhaust the cache.

The failure mode is familiar: everything works until traffic arrives, then requests start failing with out-of-memory errors or queuing for seconds. The fix is not a bigger gpu-memory-utilization value. It is deciding what the service is allowed to promise and configuring the cache and batch limits to match.

Keys, limits, and observability

An internal inference service without identity becomes a shared password. LiteLLM let us issue per-user keys, attach budgets and rate limits, and see who was consuming the GPUs. Langfuse added request-level traces, which made it possible to answer questions like “why was this agent slow?” instead of guessing.

The platform served more than ten concurrent users across RAG, agentic Kubernetes, and coding agents. Those workloads have different shapes: RAG asks a few long-context questions, an agent makes many short tool-driven calls, and a coding agent can generate for a long time. A single global rate limit is the wrong control. Per-key limits and per-model routing let each workload get a share without one of them monopolising the node.

BYOK integrations for Claude Code, OpenCode, and other OpenAI-compatible tools were part of the same idea: give people a familiar client, point it at the internal endpoint, and keep the credentials and usage inside the platform.

The CUDA upgrade: 12.2 to 13.1

New vLLM and Ollama releases, and the frontier open-weight models people wanted to run, eventually required a newer CUDA stack. The node was on CUDA 12.2. The target was 13.1. On a laptop this is a package upgrade. On a shared DGX with existing GPU jobs, it is a change window with a rollback plan.

The naive approach — upgrade the driver and see what breaks — is how a maintenance window turns into an outage. We treated it as a compatibility project:

  1. Inventory the consumers. Every container image, PyTorch version, vLLM build, Ollama build, and custom CUDA job that touched the GPUs.
  2. Pin the target stack. Driver, CUDA toolkit, container toolkit, and framework wheels are a set. Mixing versions is where the weird errors come from.
  3. Test the matrix. Existing GPU jobs had to still run on the new driver, not just the new model server. Backward compatibility was the acceptance criterion.
  4. Stage the upgrade. Validate on a non-production node or a subset of GPUs first. Run a real workload, not a nvidia-smi smoke test.
  5. Keep a rollback path. Old containers, old images, and a documented way to restore the previous driver.
  6. Communicate the window. People plan around GPU availability. A silent upgrade is a support ticket generator.

Most of the pain was not the driver itself. It was the long tail: an older image that expected a CUDA 12 runtime, a framework build that had not caught up, a container that needed the NVIDIA container toolkit to expose the new driver correctly. The upgrade only looked successful when the existing jobs ran, not when the new model started.

What I would do differently

I would separate the node into clearly owned GPU slices from the start. One set for interactive chat, one for batch embedding and fine-tuning, one for experiments. Shared access is convenient until a fine-tuning job consumes the memory an interactive service needs.

I would also make model deployment declarative. A model version should be a configuration change with a recorded image, flags, quantisation, context limit, and rollback target — not a shell history entry. That makes it possible to answer “what exactly was running last Tuesday?”.

And I would write the upgrade runbook before the first upgrade. The second one is easier; the first one teaches you what the runbook should contain.

Takeaways

  • Measure worst-case latency. Averages hide the queue.
  • Treat VRAM as a scheduling problem. The model fitting is the beginning, not the end.
  • Put a proxy in front. One OpenAI-compatible endpoint buys you the freedom to change engines.
  • Give every consumer an identity. Keys, limits, and traces are operational features, not enterprise decoration.
  • Treat driver upgrades as compatibility projects. The new model working is not the test; the old jobs working is.
