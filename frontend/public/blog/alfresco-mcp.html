Wrapping Alfresco in an MCP server

Alfresco · MCP · Documents

Alfresco is the kind of system an organisation already trusts: documents, metadata, permissions, and workflows in one place. The question was whether an agent could use it without a bespoke integration for every task. The answer was to wrap the backend APIs as a network MCP server, so the agent sees document and workflow operations as tools.

The proof of concept is in Alfresco-mcp-IPR-fork.

Why MCP instead of direct API calls

Direct API calls work when the integration is fixed. They become expensive when the agent needs to discover capabilities, when several hosts need the same tools, or when the tool surface changes. MCP gives a standard description of what the server can do, so the agent runtime does not need a new adapter for every system.

For a document management system, that surface is naturally tool-shaped: search, read metadata, fetch content, list workflows, start a workflow. Each one is a bounded operation with clear arguments. That is a good fit.

The architecture

The MCP server sits between the agent and Alfresco’s REST APIs. It authenticates to Alfresco, translates tool calls into API requests, and returns compact results. The agent never sees raw API pagination or session tickets unless the tool exposes them.

  • Search and metadata tools answer “where is this document?” and “what does the system know about it?”.
  • Content tools fetch a document or a rendition for reading.
  • Workflow tools list and inspect process state.

The first version was deliberately read-heavy. Reading is where most of the value is during testing, and it is where a mistake is recoverable. Write tools came later, behind a narrower permission and an approval step.

What was hard

Authentication. Alfresco uses tickets and sessions, not a simple static token. The MCP server has to hold credentials, refresh them, and avoid leaking them into tool output. Logging in as a service identity with the smallest permissions was the starting point.

Permissions mapping. Alfresco has its own access model. A tool that returns search results must respect what the calling identity is allowed to see. It is tempting to use an admin account so search “just works”; that quietly turns the agent into a data exfiltration path. The agent should see exactly what its identity can see.

Large content. Documents can be large. Returning a full PDF into a model context is wasteful and often impossible. The useful design is to return metadata and a small excerpt, then fetch content only when the task needs it.

Pagination and shape. Raw API responses are verbose. Tools need to summarise, page, and select fields. A smaller, stable output shape is easier for the model to use and cheaper in tokens.

Write safety. Starting a workflow or changing metadata is a real action with real consequences. Write tools need explicit confirmation, idempotency where possible, and an audit record of who asked for what.

What I would do next

I would add an approval queue for write operations, similar to the Kubernetes platform: the agent proposes an action, a human approves it, and the MCP server performs it as a scoped identity. I would also add integration tests that run the same scenarios against a staging Alfresco instance, so the tool contract is tested rather than assumed.

The broader point is that MCP is a thin layer over an existing system. The hard work is not the protocol; it is respecting the system’s permissions, shaping its data for a model, and deciding which actions should require a human.
