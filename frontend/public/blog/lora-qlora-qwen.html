LoRA, QLoRA, and a mixture of adapters

Fine-tuning · LoRA · Qwen

RAG is good at pulling facts out of documents. It is less good at teaching a model a house style, a vocabulary, or a narrow answer format. That is the gap fine-tuning fills. At IPR I fine-tuned Qwen 3.5 9B on curated administrative Q&A, first with LoRA and then with QLoRA using Unsloth, and experimented with a mixture-of-LoRAs router where one base model serves several adapters.

Why fine-tune when RAG exists

These techniques solve different problems. RAG changes what the model can see. Fine-tuning changes how the model behaves. For administrative questions, RAG is the right default because policies change and the source must stay authoritative. Fine-tuning helped with the edges: consistent phrasing, a compact answer format, and better handling of the organisation’s shorthand.

It also reduced prompt size for some tasks. If the model already knows the expected structure of an answer, the prompt does not have to explain it on every request. That matters at concurrency, where every saved token is real latency.

LoRA in one paragraph

LoRA freezes the base model and trains small low-rank matrices that are added to selected layers. Instead of updating billions of parameters, you train a few million. The adapter is a separate file, often tens of megabytes, that can be loaded on top of the base model. Rank and alpha control capacity and strength; target modules decide which layers get adapted.

The practical benefit is that you can keep one copy of the base model and swap adapters for different tasks. The practical risk is that a low rank is not enough to learn a complex change, or that it is enough to damage behaviour you wanted to keep.

QLoRA: fine-tuning when memory is tight

QLoRA quantises the frozen base model to 4-bit and trains LoRA adapters on top. It cuts memory enough to fine-tune a model that would otherwise not fit, at the cost of some speed and a little quality. For a 9B model on shared GPUs, that trade was worth it.

Unsloth made the training loop faster and less memory-hungry, which mattered because the GPUs were shared with serving workloads. The less time and memory a training run consumes, the less it interferes with the people using the inference service.

The part that decides the result: data

Model quality followed data quality almost exactly. The training set was built from common administrative questions and answers drawn from the same policy material used by the RAG system. The work was less about hyperparameters and more about curation:

  • Real questions. Questions written the way employees actually ask them, not the way a policy document phrases them.
  • Short, grounded answers. If the answer could not be supported by a source passage, it did not belong in the training set.
  • Deduplication. Near-duplicate examples inflate the set and teach the model to memorise one phrasing.
  • A held-out set. Examples the model never sees during training, used to compare runs honestly.
  • Leakage checks. The same question must not appear in both training and evaluation with different answers.

A small, clean dataset beat a larger, noisy one. That is not a slogan; it was the most repeatable result of the project.

Mixture of LoRAs

The interesting experiment was serving several adapters from one base model. Instead of loading a separate full model per task, the router picks an adapter based on intent. One base model stays resident in GPU memory, and each task gets a small adapter swap or a multi-adapter batch.

This is attractive on constrained hardware because the expensive part — the base weights — is shared. It is also a clean separation of concerns: the base model provides general language ability, and each adapter owns a narrow behaviour.

It introduces its own problems:

  • Routing errors. If the router picks the wrong adapter, the answer is confidently wrong in the wrong style. Routing needs its own evaluation.
  • Adapter memory. Adapters are small, but not free. Loading many at once still competes for VRAM.
  • Versioning. An adapter is a model artifact. It needs a version, a training dataset hash, and an evaluation result, or nobody can reproduce it.
  • Train/serve consistency. The prompt template used in training must match the one used at serving time. A silent template change can degrade an adapter without any error.

What broke

  • Overfitting to phrasing. Early adapters reproduced training answers almost verbatim. More varied questions and a stricter held-out set fixed it.
  • Catastrophic forgetting. A narrow adapter became worse at general conversation. Mixing in a small amount of general data preserved the base behaviour.
  • Evaluation by inspection. A few good-looking answers are not an evaluation. A fixed set with expected key facts made comparisons meaningful.
  • Memory surprises. Quantisation reduced memory, but sequence length and batch size still drove peaks. The training configuration had to leave headroom for the serving workloads on the same node.

What I would do next

I would treat adapters as deployable artifacts with the same discipline as model servers: a registry, a version, an evaluation report, and a rollback path. I would also test the mixture-of-LoRAs router against a single general model on the same questions, because the value of specialisation is easy to assume and harder to prove.
